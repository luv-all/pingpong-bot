# 비전 파이프라인 재설계 — 검출부터 궤적까지

> 포스터용 요약. 상세 설계 근거는 [`docs/better-vision.md`](./better-vision.md), 원본 PR은 [#17](https://github.com/luv-all/pingpong-bot/pull/17).

## 문제

같은 색이면 다 검출되는 현상이 있었다. 바닥에 놓인 탁구공, 살구색 벽, 피부·옷처럼 공과
색이 겹치는 정지 물체가 매 프레임 오검출을 냈다.

## 구조: 레이어 캐스케이드

```text
Frame ─▶ Detector ─▶ Candidate ─▶ EKF ─▶ Trajectory ─▶ 기구학
```

`Detector`는 레이어를 순서대로 통과시켜 마스크를 좁혀가는 캐스케이드다. 각 레이어는
마스크에서 픽셀을 **끄기만** 하고 원본 프레임은 건드리지 않으므로, 순서를 바꾸거나
레이어를 추가/삭제해도 뒤 단계가 깨지지 않는다. 싼 연산부터 앞에 둔다.

| 순서 | 레이어 | 무엇을 끄나 |
| --- | --- | --- |
| 1 | **Background** (MOG2) | 움직이지 않는 모든 것. fly_04 기준 전경 비율 0.04% |
| 2 | **ColorBox** / ColorPlane | 남은 픽셀 중 공 색이 아닌 것 |
| — | **Picker** (종단) | 레이어가 아니라 최종 선택자. contour별 반지름·원형도로 걸러 기대 반지름과 가장 가까운 것 하나를 pick |

배경 차분을 먼저 두는 이유: 정지한 오검출원(바닥의 공, 벽)을 색 판별 전에 지워야
색 레이어가 "진짜 공 색"만 남은 후보 위에서 일하게 된다. 배경차분만으로는 부족한데,
움직이는 팔·그림자도 전경으로 잡히기 때문이다 — 그래서 색 레이어가 뒤따른다.

### Picker: 원형도 + 넓이로 하나를 고른다

```rust
// src/vision/detect/pick.rs
pub fn passes(&self, c: &Candidate) -> bool {
    return c.radius_px >= self.min_radius_px
        && c.radius_px <= self.max_radius_px
        && c.circularity >= self.min_circularity;
}
```

반지름 밴드는 캘리브레이션에서 나온 기대 반지름(테이블 대표점 5곳에 공을 투영)을
0.5~1.8배로 벌린 것이고, 원형도 하한은 하한 필터로만 쓴다 — 순위 매기는 데는 안
쓴다. 빠른 공일수록 모션 블러로 타원이 되어 원형도가 떨어지므로, 원형도로 순위를
매기면 빠른 공이 불리해진다. 최종 선택은 **기대 반지름과의 편차가 가장 작은 것**.

### 색 판별 — 상자 vs. 판별면

- **ColorBox**(현재 기본): `tune-colormask`가 만든 HSV/YCrCb 축 정렬 상자로 `inRange`.
  양성 표본만으로 만들어지므로 배경이 같은 상자에 들어오면 못 가른다.
- **ColorPlane**(대안): 양성·음성 표본으로 Fisher 선형 판별 `w = Sw⁻¹(μ_pos − μ_neg)`을
  피팅해 반공간 하나로 자른다. 상자는 공을 더 담으려면 모든 방향으로 커지는데 배경이
  바로 옆에 붙어 있어 하한을 풀면 오검출이 5 → 382로 늘었다. 판별면은 음성이 없는
  방향으로만 민다. 아직 음성 표본 파이프라인이 없어 미배선 상태.

## 계약: `Trajectory`

제어 쪽이 받는 건 접수 평면 몇 개의 점이 아니라 궤적 계약 하나다.

```rust
pub struct Trajectory {
    pub seq: u64,           // 공 인덱스
    pub origin: Instant,    // t = 0 실제 시각
    pub measured: Track,    // 관측으로부터 계산된 궤적
    pub predicted: Track,   // 예측된 궤적, Trigger 기준부터
}

pub struct State {
    pub t: Duration,
    pub position: Point3,          // [m]
    pub velocity: Vector3,         // [m/s]
    pub sigma_position: Vector3,   // 축별 1σ [m] — 스칼라로 합치지 않는다
    pub sigma_velocity: Vector3,   // 축별 1σ [m/s]
    pub spin: Option<Vector3>,     // [rad/s]
}
```

`trajectory.predicted.at_plane(0.20)?`, `at_time(Duration::from_millis(300))?`처럼
평면이나 시각을 넣으면 보간된 값이 나온다. 몇 개 평면을 어디에 둘지는 제어가
정한다 — 비전은 로봇 도달 범위(`InterceptWindow`)를 모른다.

## 무엇이 바뀌었나

- **재귀 필터(EKF) → 일괄 적합.** 비행 0.5초 40프레임을 다 들고 있다가 탄도 하나를
  가우스-뉴턴으로 맞춘다. EKF는 관측을 못 들고 있을 때 쓰는 기법인데, 여기선 다
  들고 있어도 된다. 리드타임별 타점 오차가 재귀 EKF 대비 절반 이하로 줄었다
  (0.4s: 15.0→7.0cm, 0.1s: 11.6→4.0cm).
- **관측이 3D 점이 아니라 픽셀.** 두 카메라는 하드웨어 동기가 없어 최대 18.9ms
  어긋난다. 삼각측량은 "두 시선이 같은 순간"을 가정하므로 5m/s 공이면 9.5cm가
  틀어진다. 픽셀은 각자 자기 시각에 쓰이므로 이 가정이 없고, 한쪽만 본 프레임도
  안 버린다.
- **궤적 종료 조건 셋.** 연속 이탈 3회 / `v_y >= 0`(돌아가는 중) / `|v| < 1 m/s`(정지).
  없을 때 잔차 15.7px → 넣은 뒤 7.4px.
- **바운스가 테이블 밖 허공에서도 일어나던 버그.** 예측기는 테이블을 무한 평면으로
  봤는데 물리 엔진(Rapier) 콜라이더는 유한해서, 둘이 같은 물리를 공유한다는 전제가
  깨져 있었다. 공 중심이 상판 위(가장자리는 반지름만큼 여유)일 때만 튀도록 수정.
- **모듈 정리.** `src/detector`(2448줄)와 `src/estimator`의 추정 절반을 삭제. 물리
  커널(ballistics·bounce·kinematics)은 `src/physics/`로, `Prediction`류는
  `src/robot/motion/`으로 이동 — 타입은 그대로 옮기기만 했다.

- **y0.08~y0.35** — 접수 창 평면들. 그 자리에서 라켓이 빗나가는 거리[cm] (면내
  x·z, y는 평면이 고정하므로 안 셈). **제어가 제일 볼 값.**
- **0.4s~0.1s** — 실제 도달까지 남은 시간별 타점 오차[cm]. "지금 커밋하면 얼마나 틀리나."
- **RMSE** — 얼린 예측과 실제 궤적이 겹치는 구간 전체 오차[cm].
- **라켓 오차는 대체로 2~6cm.** 공 지름 4cm, 라켓 15cm 기준이면 맞기는 하는 수준.
  `fly_11`만 21cm로 혼자 나쁘다(트랙이 20번 끊김, 원인 미조사).
