## 2. 핵심 통찰 — 이 로봇은 히터가 아니라 **블로커**다

임팩트 모델:

```
v_out·n = (1+e)·(v_r·n) − e·(v_in·n)
```

실측값을 넣으면:

| 항 | 값 | 계수 | 기여 |
|---|---|---|---|
| `v_r·n` (스윙) | **0.18** | ×1.53 | 0.28 |
| `v_in·n` (입사) | **−4.36** | ×0.53 | **2.31** |

**출사 속도의 89%가 공 자신의 반발에서 오고, 스윙 기여는 11%다.**

민감도로 보면 결론이 분명하다:

- `∂(v_out·n)/∂(v_r·n) = 1 + e = 1.53`
- `∂(v_out·n)/∂(v_in·n) = −e = −0.53`

절대량이 `v_in·n = 4.36` vs `v_r·n = 0.18`이라, **입사 속도 20% 증가가 스윙 속도
300% 증가와 같은 효과**를 낸다. 스윙은 이 식에서 **가장 레버리지가 낮은 항**이다.

> 이것이 오늘 시도한 플래너 레버 5개가 전부 무효였던 이유다. 옳은 축을 안 밀고
> 있었다.

그리고 결정적으로, **지배적인 두 항 `e`와 `v_in`이 둘 다 실측이 아닌 보수적
추측값**이다 (§4).

## 4. 융합 해결책 — 지배 항부터 민다

원칙: **`v_out·n` 식에서 계수×절대량이 큰 항부터.** 스윙은 마지막이다.

### A. 입사 조건 최적화 ★ 가장 큰 레버, 그리고 우리 통제 하

`v_in·n`을 4.36 → 6.0으로 올리면:

```
v_out·n = 1.53(0.18) + 0.53(6.0) = 0.28 + 3.18 = 3.46
```

**적법한 리턴에 필요한 3.44를 지금 스윙 그대로 넘긴다.**

반직관적이지만 모델의 직접 귀결이다 — 블로커에게는 **빠른 공이 더 쉽다**.
그리고 이전 세션에서 "현실성"을 이유로 슈터를 7.1 → 6.0 m/s로 낮춘 것이
**정확히 반대 방향**이었다.

⚠️ 트레이드오프: 빠를수록 반응 시간이 짧고 탄도가 낮아진다. commit 창
(`min_swing 0.08 ~ 0.35 s`)과 접수 가능성이 상한을 만든다. **스윕해서 최적점을
찾아야 한다** — 채점 정정 후 기준으로 다시.

### B. `e_eff` 실측 ★ 두 번째로 큰 레버

`impact().racket_effective_restitution = 0.55`는 **문서에 "튜닝값"이라고 명시**돼
있고, 문헌상 실제 러버는 **0.6~0.9**다. 0.75라면:

```
v_out·n = 1.75(0.18) + 0.75(4.36) = 0.32 + 3.27 = 3.59   → 적법 리턴 달성
```

측정 절차는 `docs/measure-physics.md` §3에 이미 있다 (장착 라켓 면에 공을 맞혀
법선 속도비). **추측을 데이터로 바꾸는 것이라 "시뮬 유리하게"가 아니다.**

### C. 목표 `v_out` 재정식화

`rally_return_velocity`가 **상대 코트 정중앙에 0.55초**라는 가장 빡센 목표를
고정으로 쓴다. 루브릭은 코트 안 아무 데나면 3점이다.

바꿀 형태: **네트를 넘고 코트 안에 떨어지는 `v_out` 집합 중 필요 `v_r`이 최소인
것**을 고른다. `rally_time_to_bounce = 0.55`와 목표점 `LENGTH×0.75`라는 두 임의
상수가 이 최적화에 흡수된다.

예: `(0, 2.0, 3.0)`이면 네트 23 cm 여유, y=1.46 착지(3점), `|v_out|` 4.22 → 3.61.

속도 derate는 근거가 없다. 공(2.7 g)·링크(0.04~0.08 kg)가 가벼워 실제는 무부하에

절차: `docs/measure-physics.md` §6 (계단 응답).

### G. 스윙을 "도달"이 아니라 "가속"으로 재설계 ★ 구조적 결함

**참고 자료**: `~/Downloads/CleanShot 2026-07-05 at 15.10.44.mp4` — Fusion 360에서
사람이 라켓을 손으로 끌어 만든 모션. 동역학 검증은 없지만 **관절 한계 안의 유효한
자세열**이고, 설계 의도를 보여준다. 팔이 완전히 접혔다 펴지며 전 관절이 수 rad씩
훑고, 라켓이 긴 호를 그리며, **임팩트 구간에서 팔이 펴져 있다.**

지금 시뮬은 `dq = [-0.033, 0, 0, -0.001]` rad — **제자리에서 속도를 만들려 한다.**

**구조적 결함**: 현재 파이프라인은 *"얼마나 빨리 칠 수 있는가"를 한 번도 묻지
않는다.*

```
임팩트 자세 IK → Jacobian 역산(순간 속도) → quintic으로 잇기 → 한계 넘으면 균일 축소
```

전부 **임팩트 순간의 국소 질문**이다. quintic은 궤적의 *모양 가정*이고, 시작
자세는 `plan_coarse_track`이 놔둔 곳 — **임팩트 자세 그 자체**라 활주로가 없다.

**빠진 개념 — proximal-to-distal 운동 연쇄.** 강하고 무거운 근위 관절
(base_pitch, 듀얼 MX-64)이 먼저 운동량을 만들고 원위 관절(wrist)이 마지막에
얹는 것. 지금은 정반대로 손목·팔꿈치가 혼자 감당하려다 균일 스케일에 깎인다.
"모든 운동은 체중을 실어야 힘이 난다"가 이것이다.

**바꿀 형태:**

1. **와인드업 자세를 관절공간에서 정의** — Cartesian 오프셋(오늘 0.12 m 시도,
   실패)이 아니라 "팔꿈치 접고 베이스 뒤로" 같은 자세. rough 단계 목표를 이걸로.
2. **스윙을 더 일찍 시작** — commit 창 `[0.08, 0.35]`와 `plan_coarse_track`이
   함께 활주로를 없앤다. 예측이 안정되면 더 이른 commit을 허용.
3. **임팩트를 스윙 *중간*에** — 정지에서 램프업해 끝점에서 V를 만드는 게 아니라,
   가속 구간을 지나며 피크 근처에서 맞힌다. 팔로스루가 이미 있으니 구조는 있다.
4. **목적함수를 "도달"에서 "최대 속도 도달"로** — 주어진 시간·한계 안에서
   임팩트점에서의 `v_r·n`을 최대화.

**천장부터 측정할 것 (코드 변경 전):** `tools/swing_bench`가 이미 quintic 없이
**순수 토크 bang-bang 폐루프**로 "이 팔이 이 임팩트에 실제로 얼마나 빨리 도달할
수 있는가"를 잰다. 이게 quintic 경로보다 훨씬 높게 나오면 **팔이 아니라 궤적
모양이 병목**이라는 뜻이고, G가 최우선이 된다. 비슷하면 팔의 한계이므로 E·F로
간다.

⚠️ `swing_bench`는 현재 프로덕션 경로를 재현하지 못한다 (단일 IK 시드 +
면고정 5제약 `velocities_for_racket_velocity` 사용). **먼저 `solve_impact_target`을
공유하도록 고쳐야** 비교가 의미 있다.

### 권장 순서

```
0(관절 리네임) → G-천장측정 → A(입사 스윕) → B(e_eff 실측)
    → C(목표 재정식화) → D(derate 실측) → G-구현 → E(마운트 세트) → F(기구)
```

- **0**은 이후 모든 논의의 어휘를 바로잡는다. 동작 무변경, 반나절.
- **G-천장측정**은 코드 변경 없이 "궤적 모양이 병목인가 팔이 병목인가"를 가른다.
  이 답에 따라 G-구현과 E의 우선순위가 갈리므로 **먼저** 해야 한다.
- **A·B**는 코드 변경 거의 없이 지배 항을 민다 (§2 감도 분석).
- **C**는 순수 소프트웨어. **D**는 E의 전제.
- **E**는 가장 크지만 세트로 묶여 있어 가장 늦다. G의 "펴진 자세" 요구와 같은
  방향이라 함께 설계하면 이득이 겹친다.

### 이것이 의미하는 것

**⚠️ 아래는 일반적인 2휠 볼머신 구조에 근거한 추론이다. 실측으로 확인할 것.**

2휠 방식이면 위·아래 휠 속도가 각각 topspin/backspin 노브에 대응하고,

- **속도 ≈ 두 휠 속도의 합**
- **스핀 ≈ 두 휠 속도의 차**

즉 **속도는 독립 조절이 아니라 top/back 조합으로 결정된다.** 지금 4/3이면 합 7,
차 +1 → 중간 속도에 약한 톱스핀.

### 시뮬과의 어긋남 — 두 가지

1. **속도**: eval의 `speed_mps = 6.0`은 **근거 없는 값**이다. HP-07의 실제 출사
   속도를 재서 맞춰야 한다.
2. **스핀**: eval이 `topspin/sidespin/drill = 0`으로 **강제**한다
   (`build_zone_shot`, `src/sim/eval_protocol.rs`). 실물은 4/3 설정이라 스핀이
   있다. 시뮬에는 Magnus 순방향과 스핀 결합 바운스가 **이미 구현돼 있으므로**,
   실측 스핀을 넣으면 입사 탄도가 달라진다.

**스핀은 §4-A와 직결된다** — top/back 조합으로 속도와 스핀을 함께 고르는 것이니,
"어떤 (속도, 스핀) 조합이 로봇에게 가장 리턴하기 쉬운가"를 시뮬에서 스윕한 뒤
그 조합에 해당하는 노브 값을 실기에 넣으면 된다. **테스트 파라미터는 우리가
정하는 것이므로 정당하다.**

### 측정해야 할 것

| 항목 | 방법 |
|---|---|
| top/back 조합별 출사 속도 | 멀티캠 삼각측량 또는 고속 촬영 후 프레임 간 거리 |
| top/back 조합별 스핀 ω | 공에 마킹 후 고속 촬영, 또는 탄도 곡률에서 역산 |
| frequency 1의 실제 간격 | 스톱워치 (eval 스케줄과 무관하지만 세션 길이 계산용) |
| oscillation 1의 스윕 폭·주기 | 좌/중/우 존 분포와 대응되는지 확인 |

**oscillation이 좌우로 자동 스윕한다면 1차 테스트의 좌/중/우 배분을 기계가
직접 만든다** — eval의 `side_yaw_deg = 10.0` 고정 조준과 어긋날 수 있다. 확인 필요.

## 7. 지켜야 할 원칙

- **현실 우선.** 시뮬 점수를 올리려고 실기 한계를 완화하지 않는다. 단 **실측
  근거로 추측값을 대체하는 것은 완화가 아니라 정밀화**다 (§4-B, §4-D가 여기 해당).
- 상수는 실값으로. 회귀가 깨지면 테스트가 틀린 물리에 맞춰져 있던 것.
- 호환 래퍼 금지 (개발 중, 배포 안 함).
- SSOT는 `src/defaults/`. 규격·치수만 `src/constants/`.
- 커밋은 논리 단위 분할. **푸시는 명시할 때만.**
- 못 치는 공은 억지 스윙 말고 스킵. 단 루브릭상 **접촉만 해도 1점**이므로
  "약해서 못 넘김"은 스킵 대상이 아니다 — "도달 불가·충돌·토크 초과"만 스킵.
- 각 단계 후 **사용자에게 테스트를 요청하고 커밋한 뒤** 다음으로 진행.

### 0단계 — 관절 축 오칭부터 바로잡는다 (동작 무변경) ★ 먼저

§3.5의 이름-실제 불일치는 **이미 두 번 잘못된 분석을 유도했다** — 초기 진단이
"베이스가 yaw니까 +Y를 못 만든다"로 샜고, 외부 분석도 "준비자세와 충돌자세 사이의

같은 함정을 밟는다.

**리네임 안:**

| idx | 현재 이름 | 바꿀 이름 | 근거 |
|-----|-----------|-----------|------|
| 0 | `yaw` | **`base_pitch`** | 축 `(-1,0,0)`, YZ평면 피치. 팔 전체를 앞뒤로 — +Y 추진 주력. 듀얼 MX-64R |
| 1 | `shoulder` | **`pan`** | 축 `(0,0,-1)`, 수직. 좌우로 돌리는 회전 (카메라 팬과 같은 의미) |
| 2 | `elbow` | `elbow` | 유지 — 실제로 팔꿈치 피치가 맞다 |
| 3 | `wrist` | `wrist` | 유지 |
